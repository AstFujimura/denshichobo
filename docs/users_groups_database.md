# ユーザー・グループ関連テーブル（DB参照用）

対象テーブルは `users`・`groups`・`group_user` の3つです。

---

## テーブル間の関係

```
users          group_user          groups
(ユーザー)  ←→  (所属関係)  ←→  (グループ)
```

- ユーザーとグループは **直接つながっていない**
- `group_user` が「誰がどのグループに入っているか」を表す
- 1人のユーザーは複数グループに所属できる
- 1つのグループには複数ユーザーが所属できる

帳簿データ（`files` テーブル）は `グループID` でグループに紐づく。  
ユーザーが帳簿を見られるかどうかは、**`group_user` にそのグループの所属があるか** で決まる。

---

## users（ユーザー）

ログインアカウント1件につき1レコード。

### カラムの意味

| カラム | DBに入る値の例 | 役割・見方 |
|--------|----------------|------------|
| `id` | `1`, `5`, `102` | ユーザーを一意に識別するID。他テーブルの `ユーザーID` はここを指す |
| `name` | `tanaka`, `astec` | ログイン時に使うユーザー名。削除済みユーザーは末尾に `(削除ユーザー)` が付く |
| `表示名` | `田中 太郎` | 画面上に表示される名前。帳簿の作成者・更新者名などに使われる |
| `email` | `tanaka@example.com` | メールアドレス。同じアドレスが複数ユーザーに存在しうる |
| `password` | `$2y$10$...` | ログインパスワード（ハッシュ値）。平文ではない |
| `管理` | `管理` または `一般` | **権限区分**。`管理` は全帳簿を閲覧可能、`一般` は所属グループの帳簿のみ |
| `削除` | 空文字 `""` または `削除` | **論理削除フラグ**。`削除` のユーザーはログインできない扱い |
| `ニュース番号` | `0`, `3` など | お知らせの既読管理用。値が大きいほど多く読んだ状態を示す |
| `パスワードリセット時` | `2024-06-01 10:00:00` | 管理者によるパスワードリセットが行われた日時 |
| `メール許可` | `0` または `1` | メール通知を受け取るか。`1` = 許可 |
| `名刺表示サイズ` | `0` または `1` | 名刺機能の表示設定。`1` = 大きい表示 |
| `email_verified_at` | 日時 または `NULL` | メール認証済み日時。未認証なら `NULL` |
| `remember_token` | ランダム文字列 または `NULL` | ログイン状態維持用。通常は気にしなくてよい |
| `created_at` / `updated_at` | 日時 | レコードの作成・更新日時 |

### DBを見たときの判断ポイント

| 確認したいこと | 見るカラム・条件 |
|----------------|------------------|
| 有効なユーザーか | `削除` が空文字であること |
| 管理者か一般か | `管理` が `管理` か `一般` か |
| 画面上の表示名 | `表示名`（なければ `name` を参照） |
| 削除済みか | `削除 = 削除`、または `name` に `(削除ユーザー)` が含まれる |

### ユーザーが新規追加されたとき、DBに現れる変化

ユーザー登録が行われると、**3テーブルにまたがって** 次の状態になる。

**users に1件追加**

| カラム | 入る値 |
|--------|--------|
| `name` | 登録されたユーザー名 |
| `表示名` | 登録された表示名 |
| `email` | 登録されたメールアドレス |
| `管理` | `管理` または `一般` |
| `削除` | 空文字 |

**groups に固有グループが1件追加**

| カラム | 入る値 |
|--------|--------|
| `id` | **users.id と同じ値** |
| `グループ名` | `{ユーザー名}(固有グループ名ghdF4ol)` |

**group_user に最低1件追加**

| カラム | 入る値 |
|--------|--------|
| `グループID` | users.id と同じ（固有グループ） |
| `ユーザーID` | users.id |
| `役職ID` | `0` |

登録時に共有グループも指定されていれば、`group_user` に **追加の行** が入る（後述）。

### ユーザーが削除されたとき、DBに現れる変化

レコードは物理削除されない。

**users の変化**

| カラム | 変化 |
|--------|------|
| `削除` | `削除` になる |
| `name` | 末尾に `(削除ユーザー)` が付く |
| `password` | 別のランダムなハッシュ値に変わる |

**group_user の変化**

- 該当 `ユーザーID` の行が **すべて削除** される（固有グループ・共有グループとも）

## groups（グループ）

帳簿の所属先・閲覧範囲の単位。1グループにつき1レコード。

### カラムの意味

| カラム | DBに入る値の例 | 役割・見方 |
|--------|----------------|------------|
| `id` | `5`, `100000`, `100001` | グループを一意に識別するID。値の範囲で種類が変わる（下表参照） |
| `グループ名` | `営業部`, `田中(固有グループ名ghdF4ol)`, `指定なし` | 画面上のグループ名 |
| `created_at` / `updated_at` | 日時 | レコードの作成・更新日時 |

### グループIDの見分け方（重要）

DBの `groups.id` の値だけで、グループの種類を判別できる。

| `id` の条件 | 種類 | 意味 | `グループ名` の例 |
|-------------|------|------|------------------|
| `id` = ある `users.id` と一致 | **固有グループ** | そのユーザー専用の個人グループ。ユーザー登録時に自動作成 | `田中(固有グループ名ghdF4ol)` |
| `id = 100000` | **システムグループ** | 「指定なし」。帳簿のデフォルト所属先 | `指定なし` |
| `id > 100000` | **共有グループ** | 複数ユーザーが所属する組織・部署単位のグループ | `営業部`, `経理` |
| `id` が小さい値（1, 2 など） | **初期データ** | 環境構築時の特殊グループ。運用中はあまり触らない | `astec(固有グループ名ghdF4ol)` など |

**固有グループの見分け方**

- `groups.id` と `users.id` が同じ
- `グループ名` の末尾が `(固有グループ名ghdF4ol)` で終わる

**共有グループの見分け方**

- `id > 100000`
- `グループ名` に `(固有グループ名ghdF4ol)` が含まれない

### DBを見たときの判断ポイント

| 確認したいこと | 見方 |
|----------------|------|
| 個人用か共有か | `id` が `users.id` と一致 → 個人用 / `id > 100000` → 共有 |
| 帳簿がどのグループに属するか | `files.グループID` と `groups.id` を結合 |
| 管理画面のグループ一覧に出るか | 共有グループ（`id > 100000`）のみが対象 |

### 共有グループが新規作成されたとき

`groups` に1件追加されるだけ。`id` は自動採番で **100001 以降** になることが多い。

この時点では `group_user` にはまだ行が増えない。メンバー追加は別操作。

### グループが削除されたとき

帳簿（`files.グループID`）が1件も紐づいていない場合のみ削除される。

削除されると同時に消える関連データ:

| テーブル | 消える条件 |
|----------|------------|
| `group_user` | `グループID` が対象グループ |
| `positions` | `グループID` が対象グループ |
| `groups` | 対象レコード自体 |

## group_user（ユーザーとグループの所属）

「どのユーザーがどのグループに入っているか」を表す中間テーブル。  
所属1件につき1レコード。

### カラムの意味

| カラム | DBに入る値の例 | 役割・見方 |
|--------|----------------|------------|
| `id` | `1`, `42` | 所属レコード自体のID |
| `グループID` | `5`, `100001` | 所属先。`groups.id` を指す |
| `ユーザーID` | `5`, `10` | 所属するユーザー。`users.id` を指す |
| `役職ID` | `0`, `3` | そのグループ内での役職。`0` = 役職なし。`0` 以外は `positions.id` を指す |
| `created_at` / `updated_at` | 日時 | レコードの作成・更新日時 |

### 役職IDの見方

`役職ID` が `0` 以外のとき、同じ `グループID` を持つ `positions` テーブルと照合する。

```
group_user.グループID = positions.グループID
group_user.役職ID     = positions.id
```

→ `positions.役職` が画面上の役職名（例: `部長`, `課長`）

### DBを見たときの判断ポイント

| 確認したいこと | 見方 |
|----------------|------|
| ユーザーが所属するグループ一覧 | `ユーザーID = 対象` の行をすべて取得し、`グループID` を見る |
| グループのメンバー一覧 | `グループID = 対象` の行をすべて取得し、`ユーザーID` を見る |
| 固有グループへの所属 | `グループID = ユーザーID` の行があるか |
| 共有グループへの所属 | `グループID > 100000` かつ `ユーザーID = 対象` の行 |
| メンバーの役職 | `役職ID` を `positions` と結合 |

### ユーザーがグループに入ったとき、DBに現れる変化

`group_user` に **1行追加** される。

| カラム | 入る値 |
|--------|--------|
| `グループID` | 入るグループの `groups.id` |
| `ユーザーID` | 対象ユーザーの `users.id` |
| `役職ID` | `0`（役職未設定）または `positions.id` |

**具体例: ユーザーID `5` が共有グループ `100001`（営業部）に部長（役職ID `3`）として入った場合**

| グループID | ユーザーID | 役職ID |
|-----------|-----------|--------|
| 100001 | 5 | 3 |

同じユーザーが複数グループに入っている場合、`group_user` には **ユーザーID が同じでグループID が異なる行が複数** 存在する。

**具体例: ユーザーID `5` の全所属**

| グループID | ユーザーID | 役職ID | 意味 |
|-----------|-----------|--------|------|
| 5 | 5 | 0 | 固有グループ（個人用） |
| 100001 | 5 | 3 | 共有グループ「営業部」で部長 |
| 100002 | 5 | 0 | 共有グループ「経理」で役職なし |

### 所属が変わったときのDBの変化パターン

| 操作 | DBの変化 |
|------|----------|
| ユーザー新規登録 | 固有グループ所属が必ず1行追加。共有グループ指定があれば追加行 |
| ユーザーの共有グループ変更 | `グループID > 100000` かつ該当 `ユーザーID` の行が一度消え、新しい所属で再作成。**固有グループの行（`グループID = ユーザーID`）は残る** |
| グループのメンバー一括変更 | 該当 `グループID` の行が一度すべて消え、新メンバー分が再作成 |
| ユーザー削除 | 該当 `ユーザーID` の行がすべて消える |
| グループ削除 | 該当 `グループID` の行がすべて消える |
| 役職の削除 | 該当 `役職ID` を持つ行の `役職ID` が `0` に変わる（行自体は残る） |

## 3テーブルを合わせて読むときの例

### 例1: 「ユーザー5はどのグループに入っているか」

```sql
SELECT gu.グループID, g.グループ名, gu.役職ID
FROM group_user gu
JOIN groups g ON g.id = gu.グループID
WHERE gu.ユーザーID = 5;
```

想定結果:

| グループID | グループ名 | 役職ID | 解釈 |
|-----------|-----------|--------|------|
| 5 | 田中(固有グループ名ghdF4ol) | 0 | 個人用グループ（必ず存在） |
| 100001 | 営業部 | 3 | 共有グループに所属、部長 |

### 例2: 「一般ユーザーが帳簿を見られるか」

1. `users.管理` が `一般` か確認
2. `group_user` からそのユーザーの `グループID` 一覧を取得
3. 帳簿の `files.グループID` がその一覧に含まれるか確認

`管理 = 管理` のユーザーは、所属に関係なくすべての帳簿を閲覧できる。

### 例3: 「固有グループと共有グループの違いをDBで見分ける」

| 観点 | 固有グループ | 共有グループ |
|------|-------------|-------------|
| `groups.id` | `users.id` と同じ | `100001` 以上が一般的 |
| `グループ名` | `(固有グループ名ghdF4ol)` を含む | 部署名など自由な名前 |
| `group_user` | 必ず1ユーザーだけ（自分自身） | 複数ユーザーが同じ `グループID` を持つ |
| 主な用途 | 個人の帳簿管理 | チーム・部署での帳簿共有 |

## よくあるDB上の状態とその意味

| DBの状態 | 意味 |
|----------|------|
| `users` に行があるが `group_user` に行がない | 異常。通常はユーザー登録時に必ず所属が作られる |
| `group_user` に `グループID = ユーザーID` の行がある | 正常。固有グループへの所属 |
| `users.削除 = 削除` かつ `group_user` に行がない | 正常。削除済みユーザー |
| 同じ `グループID`・`ユーザーID` の行が複数ある | 本来は不要な重複の可能性あり |
| `groups.id = 100000` | システム予約の「指定なし」グループ |
| `group_user.役職ID = 0` | そのグループでは役職未設定 |

## 関連テーブル（参考）

本ドキュメントの対象外だが、DBを追う際に一緒に見ることが多いテーブル。

| テーブル | 関連 | 用途 |
|----------|------|------|
| `files` | `グループID` → `groups.id` | 帳簿データの所属グループ |
| `files` | `保存者ID` / `更新者ID` → `users.id` | 帳簿の作成・更新者 |
| `positions` | `グループID` → `groups.id` | グループごとの役職名定義 |
| `schedule_group_user` | `ユーザーID` → `users.id` | スケジュール用の個人グループ（`group_user` とは別系統） |
